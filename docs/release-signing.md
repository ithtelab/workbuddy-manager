# 发布包完整性：为什么不签名了

**结论先说**：2026-10-14 起，发布包（`workbuddy-manager-v*.tar.gz`）**不再做离线私钥
签名**。更新器改为核对**发布页给的 sha256 与文件大小** —— 也就是绝大多数开源项目让
用户做的那个手工校验，这里自动做了。

本文件同时是那次取舍的记录：原来那套是怎么设计的、为什么取消、取消之后还剩下哪些
保证、以及想自己动手核对的人该怎么做。

---

## 一、现在怎么保证「装到用户机器上的包是对的」

```
GitHub Release（HTTPS，发布说明里附了 tar.gz 的 sha256）
        │
        ▼
更新器下载  →  比对大小  →  比对 sha256  →  不符即中止（不落盘、不替换、不重启）
                                        →  一致则解压 → 替换 → 重启
```

- **传输层**：包与元数据都走 HTTPS，来自项目的 GitHub Release。
- **摘要**：GitHub 的 Release API 给每个资产带 `digest`（`sha256:…`）与 `size`，
  更新器下载后逐个核对。**发布说明里也会印出同一个 sha256**，方便人工比对。
- **回退路径**：GitHub API 未认证时有 60 次/小时的限额（共享出口容易打满），
  更新器会退到 `releases/latest` 的 302 重定向。这条路拿不到摘要，此时**如实
  记成「未比对」**并把本地 sha256 打进日志，而不是假装校验过。
- **草稿与发布**：CI 建的是**草稿** Release，`releases/latest` 会跳过它 ——
  「构建中 / 还没核对」的窗口期里用户看不到这个版本（issue #127/#129）。

这套能挡住的是**实测真会发生的两类事故**：下载被截断（CDN / 代理 / TUN 链路上很常见，
截断的 tar.gz 往往解压到一半才报错，报错位置与真实原因毫无关系），以及产物在传输
途中被替换。

## 二、这套挡不住什么（本次取舍的代价）

- **挡不住「项目的 GitHub 账号被拿下」**：攻击者拿到仓库权限后可以推 tag、发版本，
  这个包有合法的摘要、会被正常装上。原来那层离线签名挡的正是这一类（他签不出名）。
- **挡不住**代码本身有漏洞 —— 那是代码审计的事。
- 镜像（GHCR）与发布包一样，只依赖账号安全 + 传输层，没有额外签名。

这不是疏忽，是权衡后的选择：签名换来的是「账号被拿下也拦得住」，代价是每次发版都要
维护者在带私钥的机器上手工签一遍（CI 里放私钥等于把防线交出去，见第五节）。取舍的
判断是：这类项目的主流做法就是「HTTPS + 发布页摘要」，而维护成本是**每次都要**付的。

## 三、迁移（老版本怎么办）

- **v1.0.86 是最后一个内置「强制验签」的版本**，它同时是「桥」：里面的更新器已经换成
  摘要校验。这样老部署不会被新版本卡死 —— v1.0.85 及更早的更新器**强制要求** Release
  上有 `.sig`。
- 为了不把旧部署锁死，后续 Release 仍会**附带一个过渡 `.sig`**（维护者本机离线私钥
  手动签名，不进 CI）；新版本的更新器不看它，只核对发布说明里的 sha256 与文件大小。
  没有这个文件的版本，停在 v1.0.85 及更早的部署会被自己的更新器拒绝。
- **已经装有 v1.0.86 或更新版本的部署**：直接更新即可，不需要签名这一步。
- **还停在 v1.0.85 及更早版本的部署**：如果当次 Release 带 `.sig`，直接点更新即可；
  如果没带（维护者漏签），两种办法二选一：
  1. 在 `.env` 里加 `WB_SKIP_SIGNATURE=1`，重启管理端，点一次更新；更新到 v1.0.86+
     之后把这个开关去掉（换了更新器就不再看它了）；
  2. 手动更新一次：下载发布包 → `bash deploy/verify-release.sh <包> <发布页的 sha256>`
     → 解压 → `sudo bash deploy/install.sh`。
- 换代之后，`WB_RELEASE_PUBKEY` / `WB_SKIP_SIGNATURE` / `deploy/release-signing-key.pub`
  都不再有任何作用，可以清掉。

## 四、想自己核对的人

一键更新已经自动核对过；手动安装时：

```bash
# 打印本地 sha256，与 Releases 页面「产物校验（sha256）」里的值比一眼
bash deploy/verify-release.sh workbuddy-manager-v1.0.86.tar.gz

# 或者把发布页上的值直接传进去，让它判定
bash deploy/verify-release.sh workbuddy-manager-v1.0.86.tar.gz <sha256>
```

Windows 一键更新脚本（`windows/update.ps1`）同样会算摘要：走 GitHub API 拿到发布页
摘要时直接比对，拿不到时只打印本地值并明说「未比对」。

## 五、附：原来那套离线签名（存档）

2026-09-11 ~ 2026-10-14 之间是这么做的，记录在此以便回看：

- `deploy/update.py` 内嵌维护者公钥（`RELEASE_PUBKEY`），下载 `.tar.gz.sig` 后用
  `ssh-keygen -Y verify` 校验，失败即中止；`WB_SKIP_SIGNATURE=1` 是逃生门。
- 私钥 `~/.ssh/workbuddy-release` 只在维护者本机，**不进仓库也不进 CI** ——
  理由：能合并 PR 的攻击者可以改 workflow 的任意步骤，把密钥打印/外传；
  密钥进了 CI，签名的全部价值（「只有你知道」）就没了。
- 它也挡不住「维护者本人被钓鱼拿到私钥」，只是把门槛从「合并一个 PR」抬高到
  「偷到离线密钥」。

取消的理由就是第一节的取舍：这层保护的收益（账号被拿下 vs 私钥被拿走，两者的
现实概率都不高）抵不上每次发版都要手工签一遍的固定成本与流程复杂度。
